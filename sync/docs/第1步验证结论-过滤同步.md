## 3. 过滤函数（可直接用于生产）

**这是本步最重要的产出**，主文档 §10.3 的 CASL 规则需与之一致。

写入 CouchDB 的设计文档：

```js
// _design/app  →  filters.by_sales
function (doc, req) {
  var user = (req && req.userCtx && req.userCtx.name)
          || (req && req.query && req.query.user) || 'anonymous';
  var salesId = (req && req.query && req.query.sales_id) || user;

  // ① 系统文档一律不下发
  if (doc._id.charAt(0) === '_') return false;

  // ② 非订单文档（产品、货源）全公司共享
  var isOrder = doc._id.indexOf('order:') === 0
             || doc._id.indexOf('orderrev:') === 0;
  if (!isOrder) return true;

  // ③ 订单按 sales_id 隔离
  if (salesId === 'admin') return true;
  return doc.sales_id === salesId;
}
```

客户端复制时引用：

```js
PouchDB.replicate(remote, local, {
  filter: 'app/by_sales',
  query_params: { sales_id: 'alice' },
});
```

## 4. 实测中发现并修掉的两个缺陷（重要）

这两个都不是测试写错，而是**会进生产代码的真缺陷**，且都属于**静默失败**。

### 4.1 🔴 过滤器把系统文档下发给了客户端

第一版过滤函数写的是：

```js
if (!isOrder) return true;   // ← 问题在这里
```

结果 Alice 的本地库出现了 `_design/app`：

```
Alice 本地文档: _design/app, order:a1, order:a2, order:a3, product:p1, product:p2
```

**危害**：服务端的过滤函数定义、`_local` 检查点等系统文档被同步到每台客户端。
虽不直接泄露订单，但属于不该下发的内部数据，且会把服务端配置散布到所有设备。

**修复**：过滤器第一条就挡掉 `_` 开头的文档（见上方 ①）。

**教训**：过滤函数必须写成**白名单式**——默认拒绝，明确放行。
写成"非 X 即放行"的黑名单式，一定会漏掉没想到的文档类型。
这与主文档 §4.5「`_id` 前缀必须严格匹配，否则静默失效」是同一类问题。

> 已加断言固化：`✓ 系统文档（_design/_local）不下发到客户端`

### 4.2 ⚠️ 过滤条件只覆盖订单会导致产品拿不到

如果过滤器只放行 `order:` / `orderrev:`，**产品数据全公司共享这条就失效了**
——销售设备上会没有产品，无法生成画册。

**正确的语义**：过滤器同时承担两件事
- 订单：按 `sales_id` 收窄
- 非订单：全量放行（除了系统文档）

## 5. 关键实现结论

| 结论 | 说明 |
|---|---|
| **必须用设计文档过滤** | `filter: 'app/by_sales'`（字符串）。PouchDB 支持传函数，但**真实 CouchDB 不接受函数**，因为函数无法通过 HTTP 序列化。生产必须用设计文档 |
| **用 `query_params` 传身份** | `query_params: { sales_id: 'alice' }`。真实环境下应改为从 JWT 的 `userCtx.name` 取，避免客户端伪造 |
| **过滤是服务端执行的** | 客户端拿到的是已经裁剪过的变更流，**不是**全量拉取后前端隐藏 |
| **冲突检测可依赖数据库** | 同 `_id` 重复写入返回 **409 conflict**，无需应用层判断 |

### 5.1 ⚠️ 安全提醒：`sales_id` 不能由客户端自由指定

本次验证用 `query_params: { sales_id: 'alice' }` 是为了方便测试。
**生产中绝不能这样**——客户端可以把它改成任何人的名字，从而看到别人的订单。

**正确做法**：`sales_id` 必须由服务端从**已认证身份**推导：

```js
var salesId = req.userCtx.name;   // 来自 JWT / session，客户端无法伪造
```

`query_params` 只用于非敏感的筛选条件。这一点必须落进主文档 §10.3。

### 10.2 🔴 复验中发现并修掉的两个真实缺陷

#### 缺陷一：过滤函数只控制「读」，不控制「写归属」

**实测**：bob 可以写入 `{_id:'order:b_forged', sales_id:'alice'}`，**写入成功**，
而且这条记录**被下发到了 alice 的客户端**，冒充成 alice 自己的单。

**修法**：在设计文档里加 `validate_doc_update`，强制订单归属等于写入者本人。

**修复后实测**：

```
bob 写入 sales_id=alice
→ {"id":"order:b_forged","error":"forbidden",
   "reason":"订单的 sales_id 必须是你本人：期望 bob，实际 alice"}
```

> ⚠️ **CouchDB 限制**：每个设计文档只能有一个 `validate_doc_update`。
> 多个设计文档都定义时**只有其中一个生效，且无任何提示**。
> 所有校验规则必须集中在同一个函数里。

#### 缺陷二：硬删除会留下永远删不掉的幽灵订单

**实测对照**：

| 做法 | 复制结果 | 客户端表现 |
|---|---|---|
| **硬删除**（`DELETE`） | `docs_read=0 docs_written=0` | 🔴 文档残留，**永远删不掉** |
| **软删除**（改 `status`） | `docs_read=1 docs_written=1` | ✅ `status` 同步为 `deleted` |

**根因**：文档被硬删除后，CouchDB 传给过滤函数的 `doc` **只剩 `_id`/`_rev`/`_deleted`**，
业务字段全部消失。于是 `doc.sales_id === salesId` 恒为 false，
**删除变更被过滤丢弃**，客户端永远收不到删除事件。

**解决方案**：**订单一律用软删除，禁止硬删除。**
改 `status` 为 `'deleted'` 并记 `deleted_at`，文档本身保留。

**副带好处**：订单是经营凭证，本就不该被物理抹掉；软删除保留完整修订历史。

### 10.3 两个缺陷的共同教训

**过滤函数的判断依据必须是「删除后依然存在的字段」。**

- 依赖 `_id` 前缀判断 → 删除后仍然可用 ✅（宽容版过滤函数实测能同步删除）
- 依赖业务字段（如 `sales_id`）判断 → 删除后字段消失，判断失效 🔴

这也解释了为什么"只按 `_id` 前缀"的宽容版过滤函数能同步删除，
而"按 `sales_id`"的严格版不能——**不是行为怪异，是字段真的没了**。

## 11. 关于同步代理实现方式（待定）

原计划复用 Aam 的 `replication-backend`（GPL-3.0，许可已兼容）。
但它是**独立的 NestJS 服务**，与主文档 §2b.5「单进程优先」冲突。

> **后续（2026-10）**：这个方案**彻底废弃了**，一天都没用上。
> 同步最终全经过本服务端代理，而代理只能用一个账号连库，
> CouchDB 的 `userCtx` 反映不了真实销售身份，于是改为**服务端授权**
> （见主文档 §10.3.4）。既然后来一行第三方代码都没用上，
> 项目许可也从 GPL-3.0 改成了 **AGPL-3.0**（理由见主文档 §2 决策 1）。

**本次复验说明**：所需的全部能力——过滤复制、校验、认证、冲突拒绝——
**用 CouchDB 自带的设计文档（一个过滤函数 + 一个校验函数）就已完整实现**，
`app/server/couch.mjs` 里两个函数加起来约 40 行。

因此**自写精简代理（甚至不需要代理，直接用 CouchDB）是更合适的路线**：
单进程、零外部服务、无额外依赖。Aam 作为参考并致谢，不直接引入其代码。

> 该决策推迟到真正把同步接进 app 时再最终确认（主文档 §16 技术债务）。
