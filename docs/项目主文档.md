## 1. 项目定位

开源、可本地化部署的双端工具，**供一家家具经销商公司内部使用**，
解决产品资料分发、电子画册生成、电子开单与多端同步问题。

**不做 ERP。** 只做三个核心动作：

1. **产品管理 + 电子画册生成** —— 管理产品数据，一键产出 PDF 画册
2. **出单记录管理** —— 销售出单，可追溯、可导出
3. **出单按销售隔离** —— 销售之间互相看不到对方出的单

### 它不是什么

| 不是 | 说明 |
|---|---|
| 不是多租户 SaaS | **同一家公司**自己部署一套，只有自己人用 |
| 不是 CRM | **系统不管理客户关系**。客户是销售在外部的自有资源，不是系统里的实体 |
| 不是渠道分销平台 | "厂家"只是货源标签，不是系统使用者 |
| 不是 ERP | 不碰库存、财务的重模块 |

### 唯一的隔离需求

**把不同销售人员的出单区分开。** 仅此一项。

销售之间要保密的是**各自的订单与成交价**——这是同公司内部最现实的泄露点
（给谁报了什么价，属于销售自己的业务资源）。
除此之外，整个系统对公司内部完全透明。

目标用户是这家经销商的销售人员，其中很多从业人员文化水平不高，
因此**所有交互必须假设用户不想学、不想看说明书、只想赶紧干完活**。

### 业务闭环

```
销售用工具挑产品 → 生成电子画册 PDF → 发给外部客户（微信/邮件）
                                          ↓
                                    客户有意向下单
                                          ↓
                     销售在工具里开单 → 电子单只存在于这个销售的客户端
                                          ↓
                          其他销售无权限看到这张单（admin 可见全部）
```

|---|---|---|---|
| 1 | 项目许可 | **AGPL-3.0** | ✅ 已定（2026-10 由 GPL-3.0 改为 AGPL-3.0，理由见下） |
| 2 | 使用范围 | **同一家经销商公司内部**，非多租户 | ✅ 已定 |
| 3 | 唯一的隔离需求 | **订单按 `sales_id` 过滤**：销售只看自己出的单，admin 看全部 | ✅ 已定 |
| 4 | 订单价格 | `items` 记录 **`list_price` + `actual_price`** | ✅ 已定 |
| 4b | **客户概念** | **系统不管理客户**。客户不是实体、不建档案、不做归属；订单上只存客户名称等文本 | ✅ 已定 |

| 4d | **数据权威** | **服务端 CouchDB 是权威副本**，本地库仅作缓存，可随时重建 | ✅ 已定（§2b.3） |
| 4e | **打包形态** | **先 Docker Compose，后 Windows .exe** | ✅ 已定（§2b.4） |
| 5 | 出单数据模型 | 订单不可变 + 追加式修订，`UNIQUE(order_id, version)` 原子冲突检测 | ✅ 已定 |
| 6 | 产品数据同步 | 单向（服务端 → 客户端），产品侧零冲突 | ✅ 已定 |
| 7 | 画册生成路线 | **Puppeteer + Chromium**（`pdf-catalog-generator` 已证伪） | ✅ 实测 |
| 8 | 兼容性基线 | iOS 15+ / Android 8+ | ⏳ 待最终确认 |

**决策 1 的演变（GPL-3.0 → AGPL-3.0，2026-10）**：

最初选 GPL-3.0 有实际考虑——想直接复用 Aam Digital 的 `replication-backend`
（GPL-3.0），省掉整个权限层的自研成本。但**那个方案最终没有采用**：
实测发现同步全经过服务端代理后 CouchDB 的 `userCtx` 无法反映真实用户，
于是改为服务端授权（见 §10.3.4）。既然后来一行第三方代码都没用上，
"许可兼容"这个理由就消失了。

改选 **AGPL-3.0** 的理由是本项目的性质：**它天生是个网络服务**——
销售在手机上登录中心取数、出单。普通 GPL 的开源义务只在**分发软件**时触发，
别人拿去做成在线服务卖给别人**不需要开源任何改动**；
AGPL 第 13 条把"远程网络交互"也纳入了触发条件，正好补上这个口子。

对自己人没有影响：**自己部署自己用不算分发，怎么改都不用开源**。
只有"靠它向别人提供网络服务"才要回馈源码——这是刻意的。

**决策 3 是整个权限模型里唯一需要实现的东西。** 它把原本设想的
"多租户 + 经销商隔离 + 价格映射隔离 + 客户隔离"全部收敛为**一条规则**：

```
order:    按 sales_id 过滤   → 销售只看自己出的单
其余文档  全公司可见         → 不做任何隔离
```

**为什么这么简**：同一家公司，不存在"外人"。客户是销售在外部的自有资源、
**不是系统实体**；货来自哪个厂家只是产品上的一个标签，不是权限边界。
唯一需要防的是销售之间的订单与成交价串台。

## 2b. 部署简易性要求（硬需求，不是"以后优化"）

> **产品目标原话**：**安装配置一次，后续就只是打开使用。**

这条要求**反过来决定架构**，必须在开发时就满足，否则后期无法包装。

### 2b.1 两类人，别混着看

| 谁 | 需要做什么 | 频率 |
|---|---|---|
| **销售** | 打开网址/扫码 → 登录 → 干活。**零安装、零配置** | 每天 |
| **装机的人**（你 / IT） | 部署服务端一次 | **一辈子一次** |

**销售端不涉及任何"配置"。** 真正要解决的是那"一次"能不能封成"点一下"。

### 2b.2 客户端形态：浏览器 / PWA（不做 App）

- 服务端部署在你们自己的机器上，**同时托管客户端页面**
- 销售拿到**一个网址或二维码**，打开即用
- **不需要 Capacitor / Tauri 打包 App** —— App 化会导致"每台设备装一次、升级逐台更新"，
  与"只打开使用"直接冲突

### 2b.3 🔴 服务端是权威副本（数据安全红线）

**这是本项目最重要的一条数据安全设计。**

```
CouchDB（服务端） = 权威副本，订单的最终归属
本地 PouchDB      = 缓存，可随时从服务端重建
```

带来的好处：**iOS 清理本地数据不再是丢数据的风险**。
手机被清理 → 下次打开自动从服务端全量同步回来 → 用户甚至感知不到。
**不依赖用户做任何操作**（不需要他"添加到主屏幕"、不需要他去申请持久化）。

> ⚠️ **红线：本地绝不能存在"只在本机、尚未同步到服务端"的订单。**
> 若存在，手机缓存被清理时那部分就真丢了，且用户不会知道。
>
> 落实要求：
> - 开单流程必须**先落本地、立刻尝试上行**，失败要**明确提示 + 自动重试到成功**
> - UI 上"未同步"状态必须**看得懂**（不能只显示一个图标），因为用户需要知道
>   "这单还没安全"
> - 不做"只在本地永久保存"的任何业务数据

### 2b.4 打包形态

**已定：先 Docker，后 .exe。** 开发时保持可 Docker 化的结构，后续再补安装包。

| 阶段 | 形态 | 说明 |
|---|---|---|
| 第一版 | **Docker Compose 一条命令** | 跨平台，依赖管理干净，**开发期可验证** |
| 后续 | Windows `.exe` 一键安装包 | 双击安装；需自带 Node 运行时 + 中文字体，体积较大 |

⚠️ **目标机器必须先有 Docker**（只需装一次）。若装机的人不熟 Docker，
Docker 安装本身也会成为门槛——这是 `.exe` 版本存在的理由。

### 2b.5 开发时必须满足的 4 条（否则后期包装不了）

1. **单进程优先** —— 避免"CouchDB + 代理 + 画册"三个独立服务各自配置
2. **零配置** —— 所有参数有合理默认值，不把 `.env` 暴露给用户填
3. **首次启动自动初始化** —— 权限文档、过滤函数、用户账号由**代码写入**，
   **不能让人手敲 JSON**（手敲 JSON 写错不报错，只是权限静默失效）
4. **HTTPS 自动处理** —— 浏览器同步强制要求 HTTPS；需自动生成证书
   或引导一次浏览器信任，不能让用户配证书

### 2b.6 装机流程的目标形态（最终应是这样）

```
装机的人：  下载 → 一条命令（或双击）→ 等它跑完 → 拿到一个网址和二维码
销售：      扫码 → 登录 → 开始用
```

中间所有步骤——建库、写权限文档、装字体、配证书、建账号——**全部由程序完成**。

## 3. 技术架构

### 3.1 数据流

```
┌──────────────┐         ┌──────────────┐         ┌──────────────┐
│  销售电脑 A   │         │  销售手机 B   │         │  销售电脑 C   │
│  PouchDB     │         │  PouchDB     │         │  PouchDB     │
│  全部产品数据 │         │  全部产品数据 │         │  全部产品数据 │
│  仅 A 自己的单│         │  仅 B 自己的单│         │  仅 C 自己的单│
└──────┬───────┘         └──────┬───────┘         └──────┬───────┘
       │                        │                        │
       └────────────────────────┼────────────────────────┘
                                ▼
                    ┌───────────────────────┐
                    │  同步代理层（权限过滤） │
                    │  服务器端执行          │
                    │  规则：order 按 sales_id│
                    └───────────┬───────────┘
                                ▼
                    ┌───────────────────────┐
                    │   CouchDB（中心枢纽）   │
                    │   全部订单集中存于此    │
                    │   部署在服务器/NAS      │
                    └───────────────────────┘
```

> **"本地完整库"的正确含义**：产品数据是**全公司共享**的（每台设备都有完整产品库，
> 保证离线可做画册）；**订单不是**——每台设备只有**自己出的单**。
> 原架构图写「PouchDB（本地完整库）」容易被理解成"全平台数据的副本"，必须按此澄清。

### 3.2 关键设计决策

- **产品数据**：全公司共享，每台设备保留完整副本 → 离线可生成画册
- **订单数据**：按 `sales_id` 过滤，**设备上只有自己出的单** → 销售之间天然互不可见
- 权限过滤**在服务器端执行**，客户端不参与鉴权判定
- 画册生成在**本地部署的 Node 服务**完成，不依赖公网
- **同步状态只用两个状态**：已同步 / 未同步，不显示技术细节

> ⚠️ 「画册生成在本地完成」的"本地"指**本地部署的服务**，**不是手机浏览器**。
> 手机端生成中文 PDF 不可行也无必要（详见 [§7.1](#71-🔴-pdf-catalog-generator不可用)）。

### 3.3 两套同步实现（2026-10 追加）

中心枢纽有两种实现，**数据模型与授权规则完全相同**，只有"怎么存"和"怎么同步"不同：

| | CouchDB 路线 | 自带存储路线 |
|---|---|---|
| 中心 | CouchDB 3.5 | `<数据目录>/orders.json` |
| 客户端传输 | PouchDB 复制协议 | `/api/hub/push`、`/api/hub/pull`（2 个端点） |
| 服务端代码 | `server/sync.mjs`（代理 + 授权） | `server/hubsync.mjs` + `server/orderstore.mjs` |
| 何时启用 | 设了 `COUCHDB_URL` | 没设（默认） |
| 用在 | Docker 版 | 团队版中心（双击即用的 exe） |

**为什么做了第二套**：CouchDB 在 Windows 上没有便携版（官方 issue #3028），
装它要管理员权限、要装服务，而目标用户"很多人不会用电脑"。
自带存储后，一个 exe + 一个数据文件就能双击即用。

**为什么不去兼容 PouchDB 的复制协议**（那样客户端一行都不用改）：
实测抓到了它完整的行为——`GET /db/`、`_local/<hash>` 读写检查点、
`_revs_diff`、`_changes?since=&style=all_docs`、`_bulk_docs`，
还有检查点里那套 `history` 数组。要兼容就得把这些形状**全部**做对；
错一处不会报错，只是**静默不同步**——正是这个项目反复踩过的那类故障。
自定义协议的语义是写出来的，能直接被断言。

**授权规则只有一份**（`server/authz.mjs`），两条路共用。
两边各写一套授权迟早走样，而**授权走样是安全事故**，不会有任何报错提示。

**冲突处理是乐观并发，不自动合并**：客户端要说明基于哪个修订，
与服务端不一致就判 conflict 并回报当前版本。自动合并可能把一方刚改的
成交价悄悄盖掉，那比报冲突糟得多。

客户端按 `/api/capabilities` 返回的 `syncMode` 自动选传输方式，用户无感。

## 4. 数据模型

原则：**每种业务对象独立文档类型，通过 ID 关联，不嵌套。**
新增模块时只新增文档类型，不改现有结构。

### 4.1 文档类型

```js
// 产品（全公司共享，不含价格）
{ _id: "product:xxx", name, category, specs, images[],
  supplier_id, ... }

// 出单记录（按 sales_id 隔离，销售只看自己的）
{ _id: "order:xxx",
  items: [{ product_id, qty, list_price, actual_price }],
  total, customer_name, customer_phone,   // 客户只存文本，不是实体
  sales_id, created_at, status, version,  // status: active | deleted
  deleted_at }

// 订单修订（追加式，不覆盖原单）
{ _id: "orderrev:xxx", order_id, version, snapshot, sales_id, created_at }

// 供应商 / 货源（只是产品上的一个标签，不是权限边界）
{ _id: "supplier:xxx", name, ... }
```

### 4.1.1 🔴 订单一律用「软删除」，禁止硬删除（实测确认的硬约束）

**删除订单不是删文档，而是把 `status` 改为 `'deleted'`。**

**为什么**：CouchDB 的过滤函数在文档被硬删除后**收不到文档的任何业务字段**——
传给 filter 的只剩 `_id` / `_rev` / `_deleted`。
于是 `doc.sales_id === salesId` 恒为 false，**删除变更被过滤丢弃**，
客户端会永久残留一个已经删掉的订单（幽灵订单）。

实测对照（`sync`/`app` 验证脚本均可复现）：

| 做法 | 复制结果 | 客户端 |
|---|---|---|
| **硬删除** | `docs_read=0 docs_written=0` | 🔴 文档残留，永远删不掉 |
| **软删除**（改 `status`） | `docs_read=1 docs_written=1` | ✅ `status` 同步为 `deleted`，`sales_id` 保留 |

**副带好处**：订单是经营凭证，本来就不该被物理抹掉。软删除保留完整修订历史，
与 §9 的"订单不可变 + 追加式修订"天然一致。

**落实要求**：
- 任何删除订单的入口（UI、API）都只打软删除标记
- 客户端渲染时把 `status === 'deleted'` 的单隐藏或置灰，**但不从本地库删除**
- `admin` 若确实需要彻底清除数据，属于运维操作，走单独流程，不走同步链路

### 4.2 明确**不存在**的文档类型

以下类型在原设计中存在，现已确认**不需要**，实现时不要造：

| 原设计 | 为什么不需要 |
|---|---|
| `customer:` | **客户不是系统实体**。客户是销售在外部的自有资源，系统只记录订单上的客户名称即可，不做客户关系管理 |
| `dealer:` | **同一家公司，没有经销商这个实体**。隔离按销售（`sales_id`），不按经销商 |
| `price:` 价格映射 | 不需要按经销商隔离价格。报价写在订单里，产品不挂价格 |
| `subscription:` 订阅关系 | 没有"经销商订阅厂家产品库"这回事。产品数据由公司自己维护，全公司共享 |

> 这一节是**负面清单**，作用是防止后来的实现者照着旧版设计文档，
> 把已经不存在的概念重新造出来。

### 4.3 `customer_name` 为什么是文本而不是 `customer_id`

订单上的客户信息（名称、电话）**只作记录和单据打印用**，系统不做客户主数据管理。

理由：

- 客户是销售自己的业务资源，系统不应该、也不需要替他管理
- 客户可能只是散客、装修公司、转介绍的**一次性买家**，建客户档案是负担
- 避免产生"客户归属"这种权限问题——**系统里没有客户，就没有客户归属**

### 4.4 为什么不记录"进货成本"

原设计设想"厂家批发价 → 加价 → 成交价"三层。**本场景不做**：

- 公司从哪个厂家进货、进价多少，与销售出单无关
- 销售拿到的就是产品目录和可报价区间，不需要知道成本
- **不在产品文档里放任何成本字段**，从根上消除"成本被下发到销售设备"的风险

> 若将来确实需要成本管理，应作为**独立文档类型 + 仅 admin 可见**，
> 而**不是**加在产品文档的字段里——CouchDB 的权限过滤是按文档而非按字段的，
> 字段级隐藏做不到。

### 4.5 `_id` 前缀命名规范（硬约束）

由于决定复用 Aam 的 `replication-backend`，其规则匹配方式是：

> **CASL 的 subject 对应文档 `_id` 的前缀**，例如 `_id: "Child:123"` 对应 subject `Child`。

因此命名**必须全项目统一**，否则权限规则会**静默失效**。规范：

| 规则 | 要求 |
|---|---|
| 分隔符 | 统一用**半角冒号** `:` |
| 大小写 | 统一**全小写** |
| 前缀词 | 单数、无空格，见下表 |
| 禁止 | 使用 `_` 开头的系统前缀（`_design`、`_users` 等） |

| 文档类型 | `_id` 前缀 | CASL subject |
|---|---|---|
| 产品 | `product:` | `product` |
| 供应商 / 货源 | `supplier:` | `supplier` |
| 订单 | `order:` | `order` |
| 订单修订 | `orderrev:` | `orderrev` |

> 待补：用户、角色、权限配置文档的前缀。

## 5. 出单隔离（唯一的权限需求）

### 5.1 规则

**这是整个权限模型里唯一需要实现的东西。**

```
order: / orderrev:   按 sales_id 过滤   → 销售只看自己出的单，admin 看全部
product: / supplier: 全公司可见         → 不做隔离
```

**为什么这么简**：同一家公司自己部署，不存在"外人"。客户不是系统实体，
货源只是产品标签。唯一需要防的是**销售之间的订单与成交价串台**
（给谁报了什么价，属于销售自己的业务资源）。

### 5.2 隔离在物理层面成立

- 销售设备上**只有自己出的单**，其他销售的单**根本不存在于他的本地库**
- 隔离不依赖"前端不显示"——即使有人翻本地数据库，也翻不到别人的单
- 产品数据全公司共享，不参与隔离

这比"文档里存所有订单、前端做字段级隐藏"可靠得多。

### 5.3 与离线的配合

订单是**销售自己在自己的设备上创建**的，因此：

- 离线状态可以正常开单（无需读别人的数据）
- 联网后上行同步到 CouchDB
- **不存在"看不到别人订单导致的功能缺失"**——他本来就不需要看到

### 5.4 admin 可见全部

公司管理者（admin）可以看到全部销售的单，用于对账与经营分析。
这是唯一的越权角色，规则上按 CASL 的角色匹配实现。

### 5.5 待定项

| 项 | 说明 |
|---|---|
| 销售离职后的数据归属 | 订单仍留在 CouchDB，admin 可见；是否需要"转交"给他人接手，视实际需要再定 |
| 是否需要共享单 | 若出现"两个销售合作一单"的情况，可给 `order:` 增加 `shared_with[]` 并放宽过滤规则。**当前不做** |

## 7. 已实测证伪的选型（禁止使用）

### 7.1 🔴 `pdf-catalog-generator`：不可用

**结论：无法生成中文画册。中文内容退化为乱码，且不报任何错误——属于会静默产出废品的失败模式。**

两个方案在**相同产品数据、相同图片素材**下的对照：

| 方案 | 判定 | 提取字符数 | 中文字符数 | 命中原始文案 |
|---|---|---|---|---|
| `pdf-catalog-generator` 3.1.4 | 🔴 **中文退化为乱码** | 5757 | 28（全为垃圾） | **0 / 5** |
| Puppeteer + Chromium 155 | ✅ **中文正常渲染** | 27590 | 718 | **5 / 5** |

**根因**：该库基于 `@react-pdf/renderer` → pdfkit。检查生成的 PDF：

```
字体: ['Helvetica']
内嵌字体流: 0     ToUnicode CMap: 0
```

- **只有标准 14 字体之一的 Helvetica**，WinAnsi 编码，**没有任何 CJK 字形**
- **零内嵌字体**：没有任何中文字体被打包进 PDF
- **零 ToUnicode 映射**：连"还原成文本"的能力都没有

**关键风险**：生成时**不报错、不警告，退出码为 0**，PDF 也能正常打开——
只是所有中文都变成了乱码。**若未做验证就发货，客户拿到的是废品。**

**替代方案（已采用）**：Puppeteer + Chromium。Chromium 直接使用系统 CJK 字体，
实测解析到的字体栈：

```
"Microsoft YaHei", "PingFang SC", "Hiragino Sans GB",
"Source Han Sans SC", "Noto Sans CJK SC", SimSun, sans-serif
```

> 附带的依赖风险（若仍需参考该包）：它依赖 `xlsx@0.18.5`，这是 npm 上最后一个官方版本，
> 且带 **CVE-2023-30533 原型污染**，修复版本仅存在于 `cdn.sheetjs.com`。
> 本场景解析的是自有产品表而非不可信上传文件，实际风险低，但 `npm audit` 会持续告警。

## 8. 数据迁移

**核心原则：用户只做选择，不做整理。**

用户能接受的操作上限是：点按钮、选文件、等结果。
任何需要理解列名、格式、字段映射的环节，都会导致放弃。

### 8.1 迁移流程

```
用户操作：打开旧小程序 → 截图/导出 → 把文件丢进工具 → 点"开始导入" → 完成
中间所有解析、字段匹配、图片下载、格式转换，全部由工具自动完成。
```

### 8.2 路径可靠性对照（重要修正）

原方案把"截图 + OCR"列为备选。**实测判断是它的可靠性远低于预期**：
截图是手机截屏，存在文字倾斜、表格线缺失、价格与规格混排、单位符号丢失等问题。
标称 95%+ 的识别率通常是在规整文档上测的，渠道小程序截图不属此列。

**更关键**：识别错了用户就必须**编辑**，而编辑正是本原则明确要避免的操作。

| 路径 | 可靠性 | 门槛 | 建议 |
|---|---|---|---|
| **抓接口拿结构化 JSON** | **高** | 一次技术操作（抓包） | ✅ **提升为首选技术方案** |
| 联系旧服务商导出 | 最高 | 商务门槛 | ✅ 商务层面并行推进 |
| 截图 + OCR | 低 | 低 | ⚠️ **降为兜底** |
| 重新拍照录入 | 中 | 低 | ✅ 产品数量少（50 个以内）时可行 |

**"抓接口"的可执行做法**：在电脑微信里打开旧小程序 → 抓取后端接口 →
保存 JSON → 丢进工具。用户操作量仍只是"按一次说明操作并选中文件"，
**完全符合"只做选择"原则**，且结果远比 OCR 可靠。

### 8.3 具体设计要点

- **接受任意格式**：Excel/CSV、JSON、粘贴的杂乱文本
- **模糊匹配字段**："产品名"/"名称"/"品名"自动识别为同一字段，
  价格带 `¥` 或 `元` 自动清洗
- **导入后让用户"确认"而非"编辑"**：自动生成预览卡片，用户滑一遍，
  明显错误的点删除或修改，**大部分正确内容不需要操作**
- **图片全自动处理**：自动下载、裁剪、压缩、关联，用户不需要知道图片存在哪
- **进度提示说人话**："正在导入第 23 个产品，共 156 个……"不要显示技术细节

### 8.4 工作量警示

字段模糊匹配、价格清洗、图片自动下载与压缩、进度提示——
这些是一个**完整的子产品**，不是产品管理模块的附属功能。
**必须在排期里单独立项**（见 [§13](#13-开工优先级) 第 6 步）。

## 9. 冲突处理

**订单按 `sales_id` 隔离，冲突面因此极小。** 因为一张单只属于一个销售，
其他销售根本拿不到它，所以**不存在"两个销售争同一张单"的情况**。

真正可能的冲突只有一种：**同一个销售的订单，在他的两台设备上（手机 + 电脑）
被同时修改**。

### 9.1 已定方案：结构上无法冲突

```
orders           : { _id: "order:xxx", sales_id, version: 1, ... }   // 创建后不可变
order_revisions  : { _id: "orderrev:xxx", order_id, version: 2, snapshot: {...} }
                   // 追加，不覆盖；服务端建唯一约束
                   UNIQUE(order_id, version)                          // ← 原子冲突检测
```

- **创建**：客户端生成 ULID 作为主键，天然无冲突
- **修改**：不覆盖原文档，追加一条版本记录，`version` 原子递增
- **冲突检测**：数据库对 `(order_id, version)` 建唯一约束。
  两台设备同时把同一张单改成 v2，**只有一个能写入成功**，另一个被数据库直接拒绝，
  客户端据此提示用户
- **无静默丢数据**：被拒绝的一方立刻收到明确失败，不存在"时钟不同步导致静默覆盖"
- **审计天然完备**：修订记录本身即历史

**这比 last-write-wins 和"冲突后人工裁决"都更简单**，且因为订单是低频修改对象，
存储开销可忽略。

> 原设计写"后提交的设备收到同步提示，展示冲突，由使用者决定覆盖或保留"。
> 这套做法**在隔离生效后无法实现**——被隔离的数据看不见，冲突也就看不见。
> 改为数据库层的原子拒绝后，反而更可靠。

## 10. 权限与角色模型

> 状态：✅ **已定型**。规则收敛为一条，实现量很小。

### 10.1 角色定义

| 角色 | 说明 | 数据范围 |
|---|---|---|
| `admin` | 公司管理者 | **全部订单** + 全部产品 |
| `sales` | 销售人员 | **只有自己出的单**（`sales_id` = 自己）+ 全部产品 |

**只有两个角色。** 原设计里的 `supplier`（厂家）、`dealer`（经销商）
在这个场景下不存在——同一家公司自己用，货源只是产品上的标签。

### 10.2 权限矩阵

| 文档类型 | admin | sales |
|---|---|---|
| `order:` / `orderrev:` | 读写（全部） | 读写（**仅 `sales_id` = 自己**） |
| `product:` | 读写 | 只读（全公司共享） |
| `supplier:` | 读写 | 只读（全公司共享） |

### 10.3 CASL 规则写法

权限规则以 `Config:Permissions` 文档存储在 CouchDB 中，结构如下：

```json
{
  "_id": "Config:Permissions",
  "data": {
    "public": [],
    "default": [
      { "subject": "product",  "action": "read" },
      { "subject": "supplier", "action": "read" }
    ],
    "sales": [
      { "subject": "order",    "action": ["create", "read", "update"],
        "conditions": { "sales_id": "${user.name}" } },
      { "subject": "orderrev", "action": ["create", "read"],
        "conditions": { "sales_id": "${user.name}" } }
    ],
    "admin": [
      { "subject": "all", "action": "manage" }
    ]
  }
}
```

**要点**：

- `default` 规则对所有已登录用户生效 → 产品与货源的只读权限放这里
- `sales` 角色的关键就是 `conditions.sales_id = ${user.name}`，
  `${user.name}` 是 Aam 后端提供的当前用户变量
- **`sales_id` 必须存用户名（或与用户名一致的稳定标识）**，否则规则匹配不上。
  若想用 UUID，需确认 Aam 的 `${user.name}` 是否能映射到该字段

> ⚠️ **`subject` 必须与文档 `_id` 前缀严格一致**（见 [§4.5](#45-_id-前缀命名规范硬约束)）。
> 规则匹配不上时会**静默失效**，不会报错——这是最容易踩的坑。

### 10.3.1 🔴 身份必须来自服务端认证，绝不能由客户端指定

过滤 / 权限判定用的 `sales_id` **必须由服务端从已认证身份推导**：

```js
var salesId = req.userCtx.name;   // ✅ 来自会话，客户端无法伪造
```

**绝对不要**写成从查询参数取值：

```js
var salesId = req.query.sales_id; // ❌ 客户端可改成任何人的名字，直接看到别人的订单
```

> 这一条是**整个权限模型唯一的攻击面**：过滤逻辑本身很可靠，
> 但只要身份可以被客户端指定，隔离就形同虚设。

### 10.3.4 ✅ 最终落地的授权方案：由服务端执行（第 4 步实测确认）

> **本节取代 §10.3 / §10.3.2 / §10.3.3 作为"实际生效的规则"。**
> 那三节描述的 CASL 与 CouchDB 过滤/校验函数仍然**保留**在该库的设计文档里，
> 作为**纵深防御**（若将来改成浏览器直连 CouchDB，它们会立即生效），
> 但在当前架构下**不是**授权执行点。

**为什么不能靠 CouchDB 的 `userCtx`**（第 4 步实测）：

浏览器到 CouchDB 的同步**全部经过本服务端代理**，而服务端只能用**一个**账号连 CouchDB。
于是 `userCtx.name` 永远是那个账号：

```
bob 写入自己的订单 → 403 forbidden
  "订单的 sales_id 必须是你本人：期望 app，实际 alice"
```

过滤函数同样匹配不到任何销售的单，表现为**所有销售看到的数据完全一样**——隔离彻底失效。

要让 `userCtx` 变成真实身份，需要在 CouchDB 启用代理认证
（`X-Auth-CouchDB-UserName` 头）并改配置重启服务（需管理员权限）。

**最终方案**：**服务端持 admin 身份访问 CouchDB，授权规则由服务端执行。**
规则集中在 `app/server/sync.mjs`：

```
R1  读订单：只能读 sales_id === 自己 的；admin 读全部
R2  写订单：sales_id 必须 === 自己；admin 不受限
R3  非订单文档（产品/货源等）：全公司可读，仅 admin 可写
R4  系统文档（_design 等）不下发，也不接受客户端写入
```

**为什么这样更好**：同步本来就必须经服务端代理（客户端不能持有 CouchDB 凭据），
服务端是唯一可信层。授权集中在一处、易审计；不改 CouchDB 配置、
不给每个销售建账号、不保存任何密码。

**实测成绩**：同步代理 23/23、端到端 18/18、界面 44/44。

#### 10.3.4.1 ⚠️ 代理同步时必须放行复制协议自己的端点

这一条踩过三次坑，都是同一个原因：**把协议的内部端点当业务数据来管**。

| 端点 | 错误做法 | 后果 | 正确做法 |
|---|---|---|---|
| `_local/*` | 当作系统文档拒绝 | **复制无法推进**，订单永远"未同步" | 放行（不参与复制，不含业务数据） |
| `_revs_diff` | 当作文档 id 校验归属 | 整次推送失败 | 识别为**命令式端点**并透传 |
| `_bulk_docs` 内含 `_design` | 整批 403 | 整次推送失败 | **只滤掉该条**，其余照常写入 |

最后一条尤其关键：PouchDB 推送末尾会带 `_design` 文档（存放检查点），
**整批拒绝等于整次推送失败**。必须滤掉它并回报"已跳过"，让其余文档正常落地。

#### 10.3.4.2 🔴 客户端授权必须用「绝对 URL」调用代理

```js
db.replicate.to('/api/sync/orders')                        // ❌ 网络请求 0 条
db.replicate.to(new URL('/api/sync/orders', location.origin).href)  // ✅
```

**PouchDB 只在参数是绝对 URL 时才按 HTTP 处理。** 传相对路径时它把该字符串
当成**本地数据库名**，在两个本地库之间"复制"一场：

```
push 返回: {"docs_written":1,"errors":[]}   ← 看起来完美成功
网络请求数: 0                                ← 一个包都没发
CouchDB: 什么都没有
```

这是最难查的失败模式：**所有指标都显示成功**，只有对照服务端才发现数据没动。
凡是"看起来同步成功但服务端没数据"，第一个要检查的就是 URL 形式。

### 10.3.2 真实 CouchDB 的过滤函数写法

Aam replication-backend 做的是 CASL 规则判定；若直接用 CouchDB 的
`_changes` 过滤复制，则过滤函数写在设计文档里：

```js
// _design/app → filters.by_sales
function (doc, req) {
  var salesId = req.userCtx.name;     // ← 服务端认证身份

  // ① 系统文档一律不下发
  if (doc._id.charAt(0) === '_') return false;

  // ② 非订单文档（产品、货源）全公司共享
  var isOrder = doc._id.indexOf('order:') === 0
             || doc._id.indexOf('orderrev:') === 0;
  if (!isOrder) return true;

  // ③ 订单按 sales_id 隔离；admin 可见全部
  if (salesId === 'admin') return true;
  return doc.sales_id === salesId;
}
```

> ✅ 该函数已实测通过 22 项断言，详见
> [`sync/docs/第1步验证结论-过滤同步.md`](../sync/docs/第1步验证结论-过滤同步.md)。
>
> ⚠️ **过滤函数必须写成白名单式**（默认拒绝、明确放行）。
> 实测中第一版写成"非订单即放行"，结果把 `_design/app` 等系统文档下发到了客户端。
> 黑名单式过滤一定会漏掉没想到的文档类型。

### 10.3.3 🔴 过滤只管「读」，必须再加校验函数管「写归属」

**实测发现的缺口**：过滤函数只能控制"谁能读到什么"，**不能阻止别人写一条声称属于你的数据**。

实测结果（未加校验函数时）：

```
bob 写入 {_id:'order:b_forged', sales_id:'alice'}  →  写入成功
→ 这条记录被下发到了 alice 的客户端，冒充成 alice 自己的单
```

**修法**：在设计文档里加 `validate_doc_update`，强制订单归属等于写入者本人。

```js
// _design/app → validate_doc_update
function (newDoc, oldDoc, userCtx, secObj) {
  var roles = (userCtx && userCtx.roles) || [];
  var name  = (userCtx && userCtx.name) || null;
  function isAdmin() {
    return roles.indexOf('_admin') !== -1 || name === 'admin';
  }

  var isOrder = newDoc._id.indexOf('order:') === 0
             || newDoc._id.indexOf('orderrev:') === 0;
  if (!isOrder) return;

  if (isAdmin()) return;

  if (newDoc.sales_id !== name) {
    throw({ forbidden: '订单的 sales_id 必须是你本人：期望 ' + name
      + '，实际 ' + newDoc.sales_id });
  }
  if (newDoc.total !== undefined
      && (typeof newDoc.total !== 'number' || newDoc.total < 0)) {
    throw({ forbidden: 'total 必须是非负数字' });
  }
}
```

加上之后的实测结果：

```
bob 写入 sales_id=alice  → {"error":"forbidden",
  "reason":"订单的 sales_id 必须是你本人：期望 bob，实际 alice"}
```

> ⚠️ **CouchDB 的限制**：**每个设计文档只能有一个 `validate_doc_update`**。
> 若有多个设计文档都定义了它，**只有其中一个会生效**（最后写入的赢，无任何提示）。
> 因此**所有校验规则必须集中在同一个函数里**，不要分散到多个设计文档。

**两条防线缺一不可**：

| 防线 | 管什么 | 缺失后果 |
|---|---|---|
| `filters.by_sales` | **读**：谁能看到哪些文档 | 越权读取，数据泄露 |
| `validate_doc_update` | **写**：归属是否可伪造 | 越权写入，伪造他人订单 |

### 10.4 权限撤销后的数据残留（安全边界）

Aam 的 README 明确指出：权限过滤**只能阻止新数据流入**，
已同步到设备的文档需要**客户端主动清理**，他们为此专门实现了
`permission-enforcer.service.ts`。

**对本项目的含义**：

- 本场景下**风险很小**：产品数据本来就是全公司共享的，订单数据**本来就在销售自己设备上**
- 唯一场景是**销售离职**——他的设备上仍有他自己的历史订单
- 建议 v1 就提供显式的"清除本地库"入口，作为离职交接的标准动作

> 相比原设计（需清理价格数据、客户数据），本场景的清理需求大幅简化。

### 10.5 Aam 后端的运行要求

复用需配置：`DATABASE_URL`、`DATABASE_USER`、`DATABASE_PASSWORD`、
`PERMISSION_DB`、`JWT_SECRET`、`JWT_PUBLIC_KEY`（可选 `SENTRY_DSN`）。

修改权限后需调用两个管理端点：

- `/admin/reload/{db}` —— 权限文档更新后刷新后端缓存
- `/admin/clear_local/{db}` —— **当规则放宽、用户获得更多权限时**，
  重启客户端同步流程使其拉取新可见的文档

## 11. 后续可扩展模块（插件化）

| 模块 | 难度 | 要点 |
|---|---|---|
| 库存管理 | 中 | 用 **append-only 库存变动记录**避免并发扣减冲突；等真实用户反馈后再做 |
| 财务 | 高 | 只做**收款记录和对账单**，不碰复式记账、税务、报表 |
| 收款登记 | 低 | 在 `order:` 上追加收款状态与金额，或新增 `payment:` 文档类型 |

> **客户管理已从模块列表中移除**——见 [§4.2](#42-明确不存在的文档类型)。
> 系统不管理客户，只记录订单上的客户名称。

**原则：核心轻、插件独立、同步按需过滤。**

### 11.1 ⚠️ 对"同步按需过滤"的成本修正

原承诺："新增模块时只新增文档类型和同步范围，不改核心数据模型。"

这**一半成立**：

| 部分 | 是否成立 |
|---|---|
| 新增文档类型，不改核心数据结构 | ✅ 成立，ID 关联不嵌套的设计支持得很好 |
| "同步范围"公式化，无需改同步层 | ⚠️ **不完全成立** |

原因：Aam 后端用 **CASL 规则 + `_id` 前缀**过滤，能表达"某角色能否读某类文档"，
但插件往往需要**更复杂的过滤条件**：

- 库存插件：只同步"我有权限看的仓库"的变动记录 → 需按字段值过滤
- 客户管理：只同步"我负责的客户" → 按 `owner_id` 过滤

**修正后的可验证表述**：

```
新增模块的成本 = 新增文档类型 + 一条 CASL 规则（按 _id 前缀）
需要跨字段过滤的模块，必须评估同步层改造
```

### 12.1 打包路线（已定：先 Docker，后 .exe）

> 🔴 **本机 Docker 装不了（已实测确认）**：`wsl --install` 返回 **403（被禁止）**，
> 且系统里 WSL 的 Linux 子系统功能**从未安装**。Docker Desktop 依赖 WSL2 或 Hyper-V，
> 两者都需开启 Windows 可选功能（需管理员、可能重启）——这台机器上走不通。
>
> **这不阻塞开发。** 因为应用是通过 HTTP 与 CouchDB 通信的，
> **不关心 CouchDB 跑在容器里还是原生服务上**。已改用原生 CouchDB 3.5.3
> （官方 Windows MSI，装成自动启动的 Windows 服务）完成开发与验证。
> 将来要分发给多个 NAS 时，换成 Docker 或把 CouchDB 一并内嵌进安装包，
> **应用代码一行都不用改**。
>
> 对**单一台机器自用**这个场景，原生安装其实是比 Docker 更短的路径。

| 阶段 | 形态 | 目标机需要什么 |
|---|---|---|
| **当前（开发/自用）** | **原生 CouchDB + Node 应用** | 已就绪 |
| 分发第一版 | **Docker Compose 一条命令** | 需先装 Docker（一次） |
| 后续 | **Windows `.exe` 一键安装包**（可内嵌 CouchDB） | 什么都不用装，双击即可 |

**`.exe` 版本其实是更适合"不想学"的用户的交付形态**：把 CouchDB 一起打进去，
双击装完就能用，连 Docker 都不用。Docker 的价值主要在跨平台与依赖隔离，
属于服务端运维友好的选择，不是终端用户友好的选择。

### 12.2 Docker Compose 编排（✅ 已实测通过）

```
容器 1  couchdb   订单的权威副本            不对外暴露，仅 Docker 内网
容器 2  app       服务端 + 界面 + 同步代理    不对外暴露，仅内网
                  （授权执行点）
容器 3  caddy     HTTPS 反代，自动管证书      ★ 只有它对外（80/443）
```

**对装机的人只暴露一条命令**：

```bash
docker compose up -d
```

启动后**自动完成**：等 CouchDB 就绪、建库、建 `_users`、
创建应用账号、写权限文档、打印初始密码、起 HTTPS。

**只有 Caddy 对外**——数据库与应用都在内网，减少暴露面。

**画册与同步合并在一个容器里**：Chromium 与中文字体都装进 `app` 镜像。
原计划把画册拆成独立容器，实测发现没必要——合并后仍是单进程，
少一个容器就少一处配置，符合 §2b.5「单进程优先」。

> ⚠️ **HTTPS 不是可选项**：登录密码明文过网时，密码认证形同虚设。
> Caddy 已自动处理：填 IP 用内部 CA，填域名自动申请 Let's Encrypt 可信证书。

完整部署步骤见 [`deploy/README.md`](../deploy/README.md)。
实测过程与踩到的四个 bug 见 [第 6 步验证结论](../app/docs/第6步验证结论-一键部署.md)。

### 12.3 Windows 安装包（后续阶段，暂不需要）

可复用的官方组件：CouchDB 提供**官方 Windows MSI**，支持静默安装并注册为服务。

```bat
msiexec /i apache-couchdb-3.x.x.msi /quiet INSTALLSERVICE=1 ^
        ADMINUSER=admin ADMINPASSWORD=<自动生成> /norestart
```

- 安装路径**不能含空格**（如 `C:\CouchDB`）
- Windows 8/8.1/10 需 `.NET Framework 3.5`
- 装完**必须完成单节点 Setup**，否则不可用 —— **这一步必须由安装程序自动完成**
- 需要管理员权限

> 这条也在纯 Windows 手工部署时可用，不必依赖 Docker。但**手工做就等于放弃了
> §2b 的简易性目标**，仅建议作为开发调试手段。

### 12.4 中文字体必须在镜像/安装包内固定打包

画册生成依赖系统 CJK 字体。**必须在镜像内打包中文字体**（如思源黑体），
不要依赖宿主系统的字体——**否则部署环境缺字体时，画册会静默变成乱码**，
与 [§7.1](#71-🔴-pdf-catalog-generator不可用) 是同一类失败模式。

### 12.5 装机后的交付物

装机的人做完那"一次"之后，应该拿到：

- **一个网址**（销售用它打开）
- **一个二维码**（扫一下就到同一个网址，省去手输）

销售端不需要分发任何文件、不需要装任何东西。

### 13.1 为什么出单记录要先于权限层

权限规则过滤的字段（`sales_id`）是**订单文档的一部分**。
若先做权限层，没有订单可过滤；若订单先落地，权限层只是加一条 CASL 规则。
**先有数据、再定规则**，改动面最小。

> 这与原设计"先跑同步 → 再做价格隔离 → 再做出单"的顺序不同。
> 原顺序是为多租户设计的，本场景下隔离规则简单到可以放到订单之后。

## 14. 贯穿始终的产品原则

| 场景 | 原则 |
|---|---|
| 开单界面 | 大按钮、少输入框、能选就不打字 |
| **产品与订单界面** | **图片优先**——销售认货靠图不靠型号文字（见 §14.1） |
| 产品录入 | 拍照即录入，语音输入名称 |
| 画册生成 | 一键生成，**不要参数配置页** |
| 同步状态 | 只用"已同步 / 未同步"，不显示技术细节 |
| 迁移流程 | 用户只做选择，不做整理 |
| 所有交互 | 假设用户不想学、不想看说明书、只想赶紧干完活 |

### 14.1 🔴 图片优先（对标家具行业常用小程序）

> **本节的结论来自一次真实的使用反馈**：试用时第一句话就是
> 「这个界面要有图片。对标微信小程序，诸如素图、极客家具汇这类小程序。」

用户看的是**开单页**——上面只有产品名和价格，没有图。
这直接说明：**光有正确的数据和流程不够，看不出是哪件货就等于不能用。**

**具体要求**：

| 位置 | 做法 | 理由 |
|---|---|---|
| 选产品 | **两列图片网格** | 一屏能扫到十几款；竖排列表一屏只看得见四五款 |
| 选产品 | **多选 + 一次加入** | 一单常出三五款货，每选一款关一次弹层要多按好几下 |
| 开单项 | **104px 缩略图 + 名称 + 品类 + 目录价** | 这一屏是当着客户核对货，认错款代价最直接 |
| 产品列表 | **80px 缩略图**，规格单独占行（最多两行） | 规格挤在一行会被截成「尺寸 2200×…」，等于没有 |
| 所有缩略图 | **`object-fit: contain`，绝不裁切** | 家具是大件商品，裁掉就认不出（见下） |

**⚠️ 缩略图一律用 `contain`，不要用 `cover`**：

```
contain  完整显示，四周可能留白 → 看得出是什么家具
cover    填满卡片，但会裁掉边缘 → 看着整齐，但可能裁掉关键部位
```

这是**踩过的一次判断错误**：一开始用 `cover` 想让卡片更饱满，
结果沙发只剩一条色带、茶几被切掉一半——正好违背加图的初衷。
对"确认选对货"这个用途，**看得出全貌比排版整齐重要**。

> 教训：界面"好不好看"要服从"能不能干成活"。
> 这两个目标冲突时，先保证后者。

## 15. 明确不做的事

- 不做 ERP
- **不做 CRM**——系统不管理客户关系，客户只作为订单上的文本记录
- 不做库存、财务的**重模块**（可作为插件后续加，但不膨胀核心）
- 不做复式记账、税务计算、财务报表合并
- 不试图替代专业财务软件
- **不做多租户**——一家公司自己部署一套，不服务于多家公司
- **不为了兼容极旧设备而牺牲架构简洁性**

#### ⚠️ 界面实现必须遵守的两条经验

**① 靠 `hidden` 属性控制显隐的元素，样式里必须有 `[hidden] { display:none }` 兜底**

`display` 属性会**压过** `[hidden]` 的默认 `display:none`。
实测中 `.sheet { display:flex }` 使"隐藏"的编辑弹层始终铺满全屏、拦截了所有点击，
**界面完全不可用**——而接口自检全绿，只有目视截图才暴露出来。

**② 界面验证脚本必须断言状态真的变了，不能"点一下截一张"**

第一版截图脚本点击无效也不报错，静默产出 4 张完全相同的废图。
若不比对哈希，就会拿一叠废图宣称"界面验证通过"。

**③ 验证动态重绘的元素时，不要用坐标点击**

切换使用人时弹层列表会重新渲染，页面处于重排中，
Puppeteer 的 `page.click()` 会一直等元素位置稳定而报 `Waiting failed: 10000ms exceeded`。

| 方式 | 结果 |
|---|---|
| `page.click('#whoList .item:nth-child(2)')` | ✗ 超时 |
| `page.evaluate(() => el.click())` | ✓ 正常触发 |

**这是测试方法的限制，不是应用缺陷。** 凡动态生成的元素，一律用页面内派发 `el.click()`。

**④ 测试里改表单值：必须先设 value 再派发 input**

```js
// ✓ 正确
await page.evaluate(() => {
  const el = document.querySelector(sel);
  el.value = '1000';
  el.dispatchEvent(new Event('input', { bubbles: true }));
});
```

先 `type()` 再 `dispatchEvent` 会让处理函数读到旧值，测试看似通过实则没测到东西。
