## 0. 先说三个必须处理的问题

### 0.1 🔴 文档里保留了两个已被实测证伪的选型

| 位置 | 文档写的 | 实测结论 |
|---|---|---|
| 五、技术选型 | 画册生成用 `pdf-catalog-generator` | ❌ **中文全部退化为乱码，且生成不报错**。已实测：PDF 内只有 Helvetica、零内嵌字体；5 个中文产品名命中 **0/5**。替代方案 Puppeteer + Chromium 命中 **5/5**。详见 [`../catalog/docs/画册链路验证结论.md`](../catalog/docs/画册链路验证结论.md) |
| 兼容性基线 | `iOS 7.1+、Android 4.0+` | ❌ React 18 / Vue 3 需要 ES2015+，iOS 7 缺失全部相关能力。该基线来自 PouchDB **3.x 时代**的文档页，PouchDB 现为 9.0.0 |

### 0.2 🟠 兼容性基线一节与第十二节自相矛盾

- 第五节写：`iOS 7.1+、Android 4.0+ 即可覆盖绝大多数设备`
- 第十二节写：`不为了兼容极旧设备而牺牲架构简洁性`

这两句不可能同时成立。建议**直接删除第五节的极旧设备基线**，保留第十二节的原则。

**另**：`iOS Safari 存储上限约 50MB` 已严重过时。Safari 17 / iOS 17 起按磁盘比例计：浏览器类应用单 origin 最高 60% 磁盘，非浏览器应用 15%；真正的风险不是上限而是**默认 best-effort 模式下数据可被 LRU 驱逐**，需调 `navigator.storage.persist()`。

### 0.3 🟠 「本地完整库」与「多级价格隔离」在术语上直接冲突

- 第二节架构图画的是：`PouchDB（本地完整库）`
- 第三节要求：`经销商 A 和 B 互相看不到对方的报价`

一台设备持有"完整库"，就不可能同时做到"看不到别人的价格"。

**这不是设计缺陷，而是表述问题**——下节给出这个矛盾其实已被你的价格分离设计解决，但表述必须改，否则会误导实现。

## 1. 多级价格隔离：设计是对的，但需要收紧表述

### 1.1 你的方案为什么成立

把**产品**（不含价格）与**价格映射**分开存，是正确且优雅的：

- 产品数据是**跨经销商共享的公共信息**，一份主数据即可
- 价格是**按经销商隔离的私有信息**，一份价格映射按 `dealer_id` 过滤下发
- 销售/经销商设备上**根本没有别人的价格文档** → 隔离在物理层面成立，不依赖"前端不显示"

这比在订单里做字段级权限要可靠得多。**这个设计应保留。**

### 1.2 但订单文档会重新引入泄露

文档的数据模型里：

```
出单记录：
  { _id: "order:xxx", customer_id, dealer_id,
    items[{product_id, qty, price}], total, ... }
```

`items[].price` 和 `total` **就是价格数据**。若订单按"销售可见"过滤下发，
而一个销售服务多个经销商（渠道场景里很常见），
**B 经销商的报价会通过订单文档泄露给服务 A 的同一个销售**。

### 1.3 收紧后的规则（建议写入文档）

隔离边界必须统一为 **`dealer_id`**，而不是"销售"：

```
规则 1  价格映射：按 dealer_id 过滤          → 只能拿到自己经销商的
规则 2  订单文档：按 dealer_id 过滤          → 与价格映射同一把尺子
规则 3  一台设备同时只服务一个经销商         → 或明确接受跨经销商可见性
规则 4  产品的公共数据不含任何价格字段       → 已有，保持
```

**规则 3 需要你拍板**：如果允许一个销售设备服务多个经销商，
那"价格互相不可见"这个卖点就无法成立，必须在文档里改为
"同一经销商内部可见，跨经销商不可见"。

### 1.4 架构图需要改的措辞

```
原： PouchDB（本地完整库）
改： PouchDB（该经销商可见范围内的完整副本）
```

"完整"指的是**离线可用性**（该经销商自己的数据全在本地），
不是"全平台数据的副本"。这个区别必须在文档里写清楚，否则实现者会照着字面做。

## 2. 数据模型：三处建议补充

### 2.1 价格快照（与上一版评估一致，此处更关键）

`items[{product_id, qty, price}]` 只存成交价。渠道场景下价格有三层：

```
厂家批发价  →  经销商加价  →  销售最终成交价
(list)         (dealer)      (actual)
```

只存 `actual` 会导致：改价后无法回溯是哪一层变了、折扣是否越权、毛利算不出来。

**建议**：

```
items: [{ product_id, qty, list_price, actual_price }]
```

**理由**：渠道工具的核心价值之一是"经销商之间价格可比、厂家可审计"。
少了这一层，"多级价格"只是个隔离机制，不是管理体系。

### 2.2 供应商关系的方向性

```
厂家自己维护产品数据，经销商订阅该厂家的产品库
```

这需要一个**订阅关系文档**，否则无法判断"哪些产品该同步给哪个经销商"：

```
{ _id: "subscription:xxx", dealer_id, supplier_id, status, created_at }
```

没有它，同步过滤器只能靠产品的 `supplier_id` 全量下发——那就等于所有经销商
都能看到所有厂家的产品，多厂家货源的意义就丢了。

### 2.3 `_id` 前缀必须严格遵守 CASL 的 subject 约定

由于决定复用 Aam 的 replication-backend，它的规则匹配方式是：

> **CASL 的 subject 对应文档 `_id` 的前缀**，例如 `_id: "Child:123"` 对应 subject `Child`。

你现在的命名（`product:xxx`、`price:xxx`、`order:xxx`）符合这个约定，
但**大小写和分隔符必须全项目统一**，否则权限规则会静默失效（匹配不上就默认拒绝或放行，取决于配置）。建议在文档里固化命名规范表。

## 3. 插件化与「同步按需过滤」的真实成本

文档第八节承诺：

> 新增模块时只新增文档类型和同步范围，不改核心数据模型。

这**一半成立**：

| 部分 | 是否成立 |
|---|---|
| 新增文档类型，不改核心数据结构 | ✅ 成立，ID 关联不嵌套的设计支持得很好 |
| "同步范围"公式化，无需改同步层 | ⚠️ **不完全成立** |

原因：Aam 的 replication-backend 用 **CASL 规则 + `_id` 前缀**做过滤，
能表达"某角色能不能读某类文档"。但插件往往需要**更复杂的过滤条件**：

- 库存插件：只同步"我有权限看的仓库"的变动记录 → 需要按字段值过滤，不只是按类型
- 客户管理：只同步"我负责的客户" → 按 `owner_id` 过滤

这说明：**要么插件只能做"按文档类型 + 角色"的粗粒度过滤**，
**要么同步层需要支持自定义过滤函数**（那就不是"不改同步层"了）。

**建议**：文档里把这条承诺改为可验证的表述——

```
新增模块的成本 = 新增文档类型 + 一条 CASL 规则（按 _id 前缀）
需要跨字段过滤的模块，必须评估同步层改造
```

## 4. 数据迁移：最大的隐藏工作量

第六节的流程（丢文件进来 → 自动解析 → 预览确认）**方向完全正确**，
符合"用户只做选择，不做整理"的原则。但要提醒三点：

### 4.1 截图 + OCR 的可靠性远低于文档预期

文档把 OCR 列为备选。实测经验是：**小程序截图 OCR 的真实成功率很低**——
截图是手机截屏，存在文字倾斜、表格线缺失、价格与规格混排、单位符号丢失等问题。
标称 95%+ 的识别率通常是在规整文档上测的，渠道小程序的截图不属此列。

**这会直接违背"用户只做选择"的原则**：识别错了用户就必须**编辑**，
而编辑正是文档明确要避免的操作。

### 4.2 有一条更可靠的路径被漏掉了

微信小程序的数据通常来自后端 HTTP 接口。相比截图 OCR：

| 路径 | 可靠性 | 门槛 |
|---|---|---|
| 截图 + OCR | 低 | 低 |
| **抓接口拿结构化 JSON** | **高** | 需要一次技术操作（抓包） |
| 联系旧服务商导出 | 最高 | 商务门槛 |

**建议**：把"抓接口"提升为**迁移的首选技术方案**，OCR 降为兜底。
给经销商一个可执行的做法：在电脑微信里打开小程序 → 抓取接口 → 保存 JSON → 丢进工具。
这仍符合"用户只做选择"（用户只需按一次说明操作并选中文件），且结果远比 OCR 可靠。

### 4.3 迁移功能的工作量应单独立项

字段模糊匹配（"产品名/名称/品名"归一）、价格清洗（`¥`/`元`）、
图片自动下载与压缩、进度提示——这些是一个**完整的子产品**，
不是产品管理模块的附属功能。建议在排期里单独列一项，不要并进第 2 步。

## 5. 其余需修正或澄清的点

### 5.1 冲突处理（第七节）与前文的价格隔离不一致

第七节仍写：`后提交的设备收到同步提示，展示冲突，由使用者决定覆盖或保留`。

但在价格隔离生效后，**被隔离的数据是看不见的，冲突也就看不见**。
真正的冲突只有一种：同一个经销商内两个销售改了同一张单。

**建议**：维持上一版验证过的方案——订单不可变 + 追加式修订 +
`UNIQUE(order_id, version)` 做**原子冲突检测**，由数据库拒绝，而不是靠客户端展示冲突。

### 5.2 参考项目清单需要修正

| 项目 | 文档描述 | 实际情况 |
|---|---|---|
| `pdf-catalog-generator` | 从 JSON/Excel/CSV 生成 PDF，内置 3 种布局 | ❌ **中文不可用**（实测）；实际为 4 种布局 |
| `有订单·电子图册` | 电子画册 + 报价单 + 订单管理的轻闭环参考 | ⚠️ **闭源商业 App**（贵州字节在线，`com.bytezx.ydd`，V1.0.5），**应用宝仅 11 次下载**。可作**功能形态参照**，**无法参考代码** |
| `Kontor` | 模块化设计思路，Catalog / Sales 拆成独立组件 | ❌ **名不副实**：`replikativ/kontor` 是 **Clojure 复式记账内核**，与"Catalog/Sales 组件"无关，技术栈无交集 |
| `jsync-engine` | 现代同步引擎，Delta Sync + 端到端加密 | ⚠️ 功能描述属实，但**5 天内发 34 个版本**、单人维护、README 宣称的服务端持久化不在默认依赖内。**不适合作为基础设施** |
| `Aam Digital` | 离线优先 + 权限过滤同步，服务 100+ 组织 | ✅ 成立且**非常活跃**。许可为 **GPL-3.0**（与项目许可一致，可直接复用） |
| `BillKu` | 报价→订单转化逻辑、自托管 + PWA | ✅ 成立，MIT。但它是**全套 ERP**（含库存/薪资/CRM/POS），只建议借鉴"报价→订单"转化与 Puppeteer 服务端出 PDF |
| `TriliumNext Notes` | 本地 SQLite + 自托管同步的轻量实现 | ✅ 成立，思路可参考 |

**`有订单·电子图册` 唯一值得借鉴的是它的分享形态**：链接 / 二维码分享给客户查看确认。
这与你的"生成 PDF 发给客户"是同一条链路上的两种形态，PDF 更符合离线要求，
但二维码分享在展会上更省事——可作为画册导出的一种可选形态。

### 5.3 部署：Docker 当前不可用，且 CouchDB 在 Windows 上支持有限

- **本机未安装 Docker**，第五节的"单容器部署"目前无法验证。
- CouchDB 官方**不提供 Windows 生产支持**（仅开发用途），部署目标是 NAS / Linux 服务器。
- 若目标环境是 Windows 电脑，"旧电脑跑 CouchDB"这条路会很痛苦。

**可选路径**：

| 目标环境 | 方案 |
|---|---|
| NAS / Linux | Docker Compose：CouchDB + 同步代理 + 画册服务 |
| 纯 Windows 电脑 | WSL2 内跑 CouchDB；或评估 `pouchdb-server`（CouchDB 协议子集的 Node 实现，但功能不全，需验证过滤复制是否够用） |

**另**：画册服务因含 Chromium，体积 300MB+，**不建议与同步服务塞进同一容器**。

## 6. 修正后的开工优先级

原第十节的顺序是：同步 → 产品+画册 → 价格隔离 → 出单 → 权限层。

**建议调整两处**：

```
第 1 步  PouchDB ↔ CouchDB 双向同步打通                （不变，地基正确）
         └─ 前置：先解决 CouchDB 的获取方式（Docker/WSL2/本地）

第 2 步  产品数据模型 + 画册生成                        ⚠️ 画册已有可用方案，
         └─ 直接采用已验证的 Puppeteer 路线                不必再验证选型
         └─ 但需补齐：封面 Logo、分类分节、字体打包

第 3 步  价格隔离层                                     （提前，理由见下）
         └─ 先定：一台设备是否只服务一个经销商
         └─ 同步补齐：subscription 订阅关系文档

第 4 步  出单记录模块
         └─ 不可变订单 + 追加式修订 + 原子冲突检测
         └─ items 记录 list_price / actual_price

第 5 步  权限过滤层                                     （可复用 Aam，GPL-3.0 已兼容）

第 6 步  数据迁移                                       ⚠️ 单独立项，工作量被低估
         └─ 首选"抓接口拿 JSON"，OCR 降为兜底

第 7 步  部署文档傻瓜化
```

**为什么把价格隔离提前到出单之前**：订单文档里含价格，
若先做订单再做价格隔离，订单的过滤规则要重写一遍。
**先定隔离边界，再设计订单结构**，可以避免返工。
