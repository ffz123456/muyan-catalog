## 2. 🔴 架构决策：授权放在服务端，而不是靠 CouchDB 的 userCtx

**原计划**：用 CouchDB 设计文档里的过滤函数 / 校验函数，按 `req.userCtx.name` 隔离。

**实测发现它在本架构下行不通**：浏览器到 CouchDB 的同步全部经过本服务端代理，
而服务端只能用**一个**账号连 CouchDB。于是 `userCtx.name` 永远是那个账号：

```
bob 写入自己的订单 → 403 forbidden
  "订单的 sales_id 必须是你本人：期望 app，实际 alice"
```

过滤函数同样匹配不到任何销售的单（`salesId === 'app'`），
表现为**所有销售看到的数据完全一样**——隔离彻底失效。

**要让 `userCtx` 变成真实身份**，需要在 CouchDB 里启用代理认证
（`X-Auth-CouchDB-UserName` 头）并重启服务，而那要改
`C:\Program Files\Apache CouchDB\etc\local.d\` 下的配置——需要管理员提权，本会话无法完成。

**最终采用的方案**：**服务端持 admin 身份访问 CouchDB，授权规则由服务端执行。**
规则集中在 `app/server/sync.mjs`，四条：

```
R1  读订单：只能读 sales_id === 自己 的；admin 读全部
R2  写订单：sales_id 必须 === 自己；admin 不受限
R3  非订单文档（产品/货源等）：全公司可读，仅 admin 可写
R4  系统文档（_design 等）不下发给客户端，也不接受客户端写入
```

**为什么这样更好**：同步本来就必须经过服务端代理（客户端不能持有 CouchDB 凭据），
服务端是唯一可信的一层。授权集中在一处，容易审计；
不必改 CouchDB 配置、不必给每个销售建账号、不必保存任何密码。

设计文档里的过滤/校验函数**保留**作为纵深防御——若将来改成浏览器直连 CouchDB，
它们会立即生效。

## 3. 🔴 实测中挖出的四个真 bug

四个都表现为**同一个危险症状**：单子只在本地、上不了服务端，而且**大多数不报错**。
这正对应主文档 §2b.3 的红线。

### 3.1 PouchDB 把相对路径当成"本地库名"

```js
db.replicate.to('/api/sync/orders')             // ✗ 网络请求 0 条
db.replicate.to(location.origin + '/api/sync/orders')  // ✓ 网络请求 7 条
```

**PouchDB 只在参数是绝对 URL 时才按 HTTP 处理。** 传相对路径时它把该字符串
当成**本地数据库名**，创建同名本地库、在两个本地库之间"复制"了一场：

```
push 返回: {"docs_read":1,"docs_written":1,"errors":[]}   ← 看起来完美成功
网络请求数: 0                                              ← 一个包都没发
CouchDB: HTTP 404                                          ← 服务端什么都没有
```

这是最难查的一个：**所有指标都显示成功**，只有对照服务端才发现什么都没有。

**修复**：`syncdb.mjs` 里用 `new URL(path, location.origin).href` 构造绝对地址。

### 3.2 双向复制的检查点互相污染

`PouchDB.sync()` 让 push 与 pull **共用同一个检查点存储**。pull 会把
**服务端序列号**（形如 `"16-g1AAA..."` 的字符串）写进去；之后 push 读这个检查点，
拿字符串序列号与本地数字序列号比较，判定"本地没有新变更"，于是什么都不推。

实测证据：本地 `_changes` 里明明有文档、`update_seq=1`，
但 `replicate.to()` 返回 `docs_read=0 / docs_written=0 / 无错误`。

**修复**：改用**独立的 push + pull**，并在每次同步前后清掉复制检查点
（`_local/<hash>`），保证 push 的检查点语义单一。

### 3.3 普通文档不允许下划线开头的字段

我为了标记"未同步"写了 `_unsynced` 字段，PouchDB 直接拒绝：

```
Bad special document member: _unsynced
```

下划线是 PouchDB/CouchDB 的保留前缀（`_id` / `_rev` / `_deleted` 等）。
而且那个标志属于**纯本地内部状态**，本就不该同步到服务端。

**修复**：改用 `_local/unsynced` 文档存放待上行清单。

### 3.4 我的授权规则挡住了复制协议自己的检查点

```
[403] GET /api/sync/orders/_local/4KrACh6uiZMC5X_...
  {"error":"forbidden","reason":"不能读取他人订单"}
```

PouchDB 用 `_local/<hash>` 存放**复制检查点**。我的 `canRead()` 里写着
"`_` 开头的系统文档不下发"，把 `_local` 一起挡了。
**读不到检查点，整个复制就无法推进**——订单反复推不上去、界面一直"未同步"。

同类问题还有两处，都是同一个原因（把协议的内部端点当成了业务数据来管）：

| 端点 | 我原来的处理 | 后果 | 正确做法 |
|---|---|---|---|
| `_local/*` | 403 系统文档不可读 | 复制无法推进 | **放行**（不参与复制，不泄露业务数据） |
| `_revs_diff` | 403 不接受写系统文档 | 整次推送失败 | 识别为**命令式端点**并透传 |
| `_bulk_docs` 里的 `_design` | 整批 403 | 整次推送失败 | **滤掉该条**，其余照常写入 |

最后一条尤其要注意：**不能整批拒绝**。PouchDB 推送时会在末尾带上 `_design` 文档
（存放检查点），整批 403 会让整次推送失败。正确做法是把它滤掉、
在响应里说明"已跳过"，让其余文档正常写入。

**修复**：在 `sync.mjs` 里区分「命令式端点」与「文档 id」，
并放行 `_local/*`、滤掉客户端提交的系统文档。

## 4. 🔴 补齐了一个此前只写在文档里的必做项

**换使用者后，本地必须清掉上一位的残留。**

实测：admin 登录后同步了一批单，切换到 alice 后，
**本地库里 admin 的单仍在**（`归属=admin,alice,bob`）。
服务端代理是正确拒绝下发的（403），但**本地已有副本不会被自动删除**。

这不只是测试环境污染，是真实风险：
**离职交接、换人用同一台手机，新销售会看到前任的客户与价格。**

**实现**（`syncdb.mjs` 的 `purgeUnauthorizedLocals()`）：
每次同步结束后，向服务端问"我现在能看到哪些订单"，
把本地不在这个集合里的**订单类文档**删掉（产品等共享文档不动）。

**一条重要的前提**：**离线时不做清理**。宁可暂时多留，
也不能在没确认权限的情况下误删用户自己的单。

这对应主文档 §10.4 一直登记为"待实现"的客户端权限清理逻辑，现已落地。

## 5. 端到端验证的判据（不只查界面）

这一步的验证刻意**不看界面说了什么，而是查数据真的落在哪里**：

```
【C】界面出单，验证文档真的落到 CouchDB
  ✓ 本地库里有这张单  order:20261013-19d62b14
  ✓ 该单已上行到 CouchDB（关键判据）  CouchDB 中已存在
  ✓ CouchDB 中的归属正确  alice
  ✓ CouchDB 中的金额与本地一致  4380 vs 4380

【D】界面软删除，验证 CouchDB 中标记而非消失
  ✓ 软删后 CouchDB 中文档仍存在（未硬删）
  ✓ 软删后 CouchDB 中 status=deleted
  ✓ 软删后归属字段仍在（可审计）

【E】换身份后可见集合变化
  ✓ bob 看不到 alice 的订单   归属=bob
```

**如果只看界面，3.1 那个 bug 会被完全漏掉**——界面显示"已保存"、
"已同步"，一切正常，而数据其实一个字节都没离开浏览器。

## 6. 数据流（最终形态）

```
销售浏览器
├── 本地 PouchDB (IndexedDB)  ← 列表读这里，离线可用
│     └── _local/unsynced     待上行清单（界面据此显示"未同步"）
│
│   push / pull（绝对 URL）
▼
服务端 /api/sync/orders/*     ← 授权在这里执行（sync.mjs 的 R1–R4）
│   身份来自服务端会话 cookie，客户端无法影响
│   admin 凭据访问 CouchDB
▼
CouchDB orders 库             ← 权威副本（§2b.3）
      _design/app           过滤函数 + 校验函数（纵深防御）
```
