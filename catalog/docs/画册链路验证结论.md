# 画册生成链路验证结论（实测记录）

> **定位**：这是 [`docs/项目主文档.md`](../../docs/项目主文档.md) §7.1 与 §13 第 2 步所引用的**原始实测证据**。
> 结论已并入主文档，本文件保留完整过程、复现命令与环境踩坑记录。
> **若两者不一致，以主文档为准。**
>
> 核心结论：**`pdf-catalog-generator` 不可用于中文画册，改用 Puppeteer + Chromium**

---

## 1. 结论

原技术选型中的 `pdf-catalog-generator`（npm）**无法生成中文画册**。中文内容会退化为乱码，
且不报任何错误——属于会静默产出废品的失败模式。

**已改用并验证通过**：Puppeteer + Chromium 的 HTML/CSS 排版路线。

---

## 2. 证据（同一把尺子下的对照）

两个方案使用**完全相同的产品数据、相同的 5 个产品、相同的图片素材**，
生成后对 PDF 做文本提取，与原始中文文案逐字比对：

| 方案 | 判定 | 提取字符数 | 中文字符数 | 命中原始文案 |
|---|---|---|---|---|
| `pdf-catalog-generator` 3.1.4 | 🔴 **中文退化为乱码** | 5757 | 28（全为垃圾） | **0 / 5** |
| Puppeteer + Chromium 155 | ✅ **中文正常渲染** | 27590 | 718 | **5 / 5** |

### 2.1 `pdf-catalog-generator` 的根因

该库基于 `@react-pdf/renderer` → pdfkit。检查生成的 PDF：

```
字体: ['Helvetica']
内嵌字体流: 0     ToUnicode CMap: 0
```

- **只有标准 14 字体之一的 Helvetica**，采用 WinAnsi 编码，**没有任何 CJK 字形**。
- **零内嵌字体**：没有任何中文字体被打包进 PDF。
- **零 ToUnicode 映射**：连"还原成文本"的能力都没有，因此中文被写成无意义字节。

提取出的"中文"样本（原文应为「云舒三人布艺沙发」等）：

```
颔閘钕噘夊形霏歧枤嚹欪閧觅鄒駑嚹嚹荕倨鸨缠嚹鑿愨倨愨捭嚹
```

**关键风险**：它在生成时**不报错、不警告**，退出码为 0，PDF 也能正常打开——
只是所有中文都变成了乱码。若未做验证就发货，客户拿到的是废品。

### 2.2 Puppeteer 路线为什么可行

Chromium 直接使用**系统 CJK 字体**，无需注册字体文件：

```
实际字体栈: "Microsoft YaHei", "PingFang SC", "Hiragino Sans GB",
           "Source Han Sans SC", "Noto Sans CJK SC", SimSun, sans-serif
```

提取结果中 5 个产品名**逐字命中**：

```
云舒三人布艺沙发 / 白蜡木实木茶几 / 黑胡桃玻璃展示柜 / 橡木伸缩餐桌 / 榉木落地衣帽架
```

## 3. 目视检查发现的真实排版缺陷（已修复）

**首次生成的目录页超出了 A4 高度。**

| | 实测 | A4 应为 |
|---|---|---|
| 目录页截图 | 1588 × **2622** px | 1588 × **2246** px |

`.page` 使用 `min-height: 297mm` 时，内容超长会把整页**静默撑高**；打印与截图只取
A4 高度，**超出部分直接丢失**。当时每页放 5 个产品，第 5 个产品已被挤出可见区域。

### 修复方式

1. **显式分页**：每页固定放 `PER_PAGE = 4` 个产品，按批次生成独立 `section`，不再依赖自动分页。
2. **加硬断言**：脚本实测每页 `getBoundingClientRect().height`，超过 A4 一律判定失败并
   给出可执行的修复提示（减少每页产品数或调整卡片尺寸），写入 `out/layout-report.json`。

修复后：

```
✓ 第 1 页  实测 1123px / A4 1123px
✓ 第 2 页  实测 1123px / A4 1123px
✓ 第 3 页  实测 1123px / A4 1123px
```

> **这条断言是画册功能的关键防线。** 产品数量由用户数据决定，早晚会有人加一款产品
> 导致某页溢出。没有断言就会静默丢内容，有了断言会明确失败并指出原因。

## 4. 本环境下的实现注意点（否则会重复踩坑）

| 现象 | 原因 | 处理 |
|---|---|---|
| `npm install` 报 `EPERM ... npm-cache\_cacache\tmp` | npm 默认缓存目录在工作区之外，被文件沙箱正确拒绝 | 设 `npm_config_cache` 到工作区内 |
| `npm install puppeteer` 不下载 Chromium | **npm 11 默认阻止 postinstall 脚本**（`allow-scripts`） | 手动执行 `node node_modules/puppeteer/install.mjs` |
| `spawn EPERM` | 受限沙箱禁止通过管道捕获子进程输出 | 安装/生成步骤需在非受限模式下运行一次 |
| Puppeteer「浏览器已在运行」 | 默认 profile 路径固定在系统临时目录，与残留实例冲突 | 指定工作区内的 `userDataDir`，运行前清理残留进程 |
| `page.pdf()` 报 `Protocol error (IO.read): Read failed` | 新版 Puppeteer 默认 `tagged: true`，走额外流式 IO，本环境不支持 | 关闭 `tagged`；**并用 CDP `Page.printToPDF` 直写文件**（已验证可用） |

**PDF 生成必须走 CDP 直写路径**，这是当前环境下唯一稳定的方式：

```js
const client = await page.createCDPSession();
const res = await client.send('Page.printToPDF', {
  printBackground: true,
  paperWidth: 8.27, paperHeight: 11.69,
  marginTop: 0, marginBottom: 0, marginLeft: 0, marginRight: 0,
  transferMode: 'ReturnAsBase64',
});
fs.writeFileSync(pdfPath, Buffer.from(res.data, 'base64'));
```

## 5. 数据模型的一处修正

原计划「产品图片只存缩略图或远程 URL」。但**画册要求在离线状态下生成**，
远程 URL 会导致断网时画册没有图。

**最终做法**：数据中存**本地图片路径**，生成画册时解析成 base64 data URI 内联。
这样画册 PDF 是**自包含**的，发给客户后对方无需网络，也不依赖你的服务器存活。

```js
// 关键：本地图片 -> data URI
function dataUri(rel) {
  const buf = fs.readFileSync(path.join(HERE, rel));
  const ext = path.extname(rel).slice(1).toLowerCase();
  return `data:image/${ext};base64,${buf.toString('base64')}`;
}
```

```powershell
node generate-with-puppeteer.mjs

# 3. 判定 PDF 中文是否正常
python tools/probe_pdf_text.py "out/catalog.puppeteer.pdf" out/report.json
```

## 7. 对后续工作的影响

| 项 | 影响 |
|---|---|
| 第 3 步「一键产出 PDF 画册」 | 技术路线已确定且验证通过，可直接进入产品化 |
| 部署形态 | Chromium 使运行体积显著增大（约 300MB+），**画册生成服务不宜与同步服务塞进同一个轻量容器**。建议：同步/后端容器 + 画册生成容器分开，或画册生成为独立可选服务 |
| 前端选型 | 「画册生成在本地完成」的「本地」= **本地部署的 Node 服务**，不是手机浏览器。已确认手机端生成不可行也无必要 |
| 图片存储 | 存本地路径（对象存储/静态目录），生成时内联为 base64。**不要存远程 URL** |
| 回归测试 | `probe_pdf_text.py` 应纳入 CI：任何改动后校验中文命中数，防止再次出现静默乱码 |
| 字体依赖 | 依赖运行环境的系统 CJK 字体。部署文档中必须写明字体要求，或在镜像内固定打包中文字体（**推荐后者**，避免经销商环境缺字体） |
